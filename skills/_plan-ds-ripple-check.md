# План: скилл-ревизор распространения изменений

Статус: **план, не реализация**. Жду сигнала на сборку.

## 1. Зачем

Изменение в ДС почти никогда не локально. Правка токена доезжает до молекул сама, а вот новая сущность — нет: появился Skeleton, а самодельные заглушки в других компонентах остались. Такой долг не виден ни в консоли, ни на скриншоте, и легко оседает в служебном файле, который никто не читает.

Скилл отвечает на два вопроса: **кого ещё касается сделанное** и **всё ли из задуманного доведено до конца.**

## 2. Что будет собрано

| Файл | Роль |
|---|---|
| `skills/ds-ripple-check.md` | правила: когда какой режим, как читать результат, что писать в чат, что в бэклог |
| `scripts/ds-ripple.js` | механика: сканы через `run_script`, возвращает компактный список адресов |
| правки `CLAUDE.md` | описание триггера, правило фиксации обещаний, место в чек-листах |

Разделение то же, что у ревизора целостности: механика — в скрипте (в контекст агента не попадает), решения — в скилле.

## 3. Три режима

### Режим 1 · Полнота раскатки — автоматически

Запускается после явного задания «поменяй токен / поправь компонент».

Вопрос: всё ли, что должно было измениться, изменилось.

Что ищем и почему могло не доехать:

| Признак | Причина пропуска |
|---|---|
| `--токен:` переопределён внутри компонентного селектора | локальная подмена перебивает новое значение |
| нужное свойство задано числом, а не `var(--токен)` | хардкод, компонент не участвует в системе |
| компонент вообще не ссылается на токен, хотя визуально должен | скопированный кусок стиля |
| CSS-файл компонента не в `ds.css` / `styles.css` | не подключён — правка не видна |

Вывод: список «файл · строка · причина». Пропущенное — в бэклог страницы сущности.

### Режим 2 · Места для раскатки — по триггеру

Появилась новая сущность или возможность. Никто не сломан, поэтому нужен явный поиск двойников:

- классы-двойники вне своего файла (`.sk-…`, `.spinner-…`, `.badge-…` в чужом CSS);
- блоки, повторяющие поведение нового компонента (анимация шиммера, заглушка, кастомный тултип);
- повторённые числовые значения там, где теперь есть токен.

Вывод: список компонентов-кандидатов с адресами. **Предложение, не действие.**

### Режим 3 · Итоги итерации — по триггеру

Сверка «что обещали» против «что сделали». Источник истины — **зафиксированный** список (todo + бэклоги), память о диалоге только дополняет его.

Что попадает в незакрытое: обещания «вернёмся / пока пропустим», собственные предложения агента, недоделанные части, вопросы, оставшиеся без ответа.

## 4. Триггер

Сигнал — отдельное короткое сообщение: **«закончили»** / «закончили итерацию».

- реагировать, только когда это всё сообщение или его явная суть;
- «закончили с этим разделом, теперь второй» — не триггер, переспросить одной строкой;
- ложный запуск дороже пропущенного: проверка платная, а сигнал легко повторить.

Семантика: закончена **итерация**, не сущность. Бэклог не удаляется, итогов «компонент готов» не подводится. Триггер может приходить многократно — уже записанное повторно не проверяется.

## 5. Бюджет

| Режим | Вызовы | Вывод |
|---|---|---|
| 1 · полнота раскатки | 1 × `run_script` | 10–30 строк |
| 2 · места для раскатки | 1 × `run_script` (+ до 2 точечных `grep` по найденным адресам) | 15–40 строк |
| 3 · итоги итерации | 1 × `run_script` (чтение todo + бэклогов) | 5–15 строк |
| Триггер (режимы 2+3 вместе) | **2–4 вызова** | ≈1–2 КБ |

Правила экономии:
- сначала широкий дешёвый скан по 1–2 шаблонам, затем точечное чтение **только по найденным адресам**;
- зависимости берём из `specs/_index.md` и `deps:` в спеках — страницы не читаем;
- обхода всех компонентов не бывает никогда;
- если скан пуст — прогон заканчивается на первом вызове.

## 6. Куда попадает результат

**В чат** — одна строка, без пересказа:

```
Раскатка: 4 места используют самодельный скелетон — список в бэклоге Skeleton.html. В бэклоге сущности сейчас 6 открытых пунктов.
```

Цифра открытых пунктов даётся при каждом срабатывании триггера: содержание не повторяется, но долг не растворяется в молчании.

**В бэклог страницы сущности** — пункт вида:

```
Раскатать Skeleton на компоненты с самодельными заглушками — Table (.dtable__sk),
AllocationBar (.albar__sk), Tile, DropdownList. Причина: собственная анимация
шиммера вместо .sk-*. Затронуто 4 компонента.
```

Обязательные части пункта: что раскатить · куда (адреса) · почему · сколько мест.

## 7. Защита от вырождения бэклога

Главный риск всей затеи: пункты копятся быстрее, чем разбираются, и раздел перестают читать — тот же исход, что у аудит-файла со Skeleton, только в другом месте.

| Правило | Смысл |
|---|---|
| Нет измеримого охвата — нет пункта | «затронуто N мест» обязательно; наблюдения без цифры не пишутся |
| Дедупликация перед записью | совпадение по смыслу = обновление старого пункта, не второй пункт |
| Потолок 3 новых пункта за прогон | остальное — одной сводной строкой «ещё N кандидатов» |
| Пункт = задача с адресами | не «стоит подумать о…», а «раскатать X на A, B, C» |

## 8. Честность о покрытии

Скилл ловит **типовые машинные признаки**: переопределения токенов, классы-двойники, повторённые числа. Он **не** находит расхождения без текстового следа — компонент, который рисует заглушку принципиально иначе, не отличается от любого другого CSS.

Отсюда запрет на формулировку «всё проверено, чисто». Допустимая формулировка: **«типовых расхождений не найдено»**. Разница существенная: первая создаёт ложное чувство покрытия, из-за которого реальные пропуски станут менее заметны, чем сейчас.

## 9. Фиксация обещаний в момент появления

Встречное правило, без которого режим 3 работает по неполным данным: длинные итерации подрезаются, часть диалога физически исчезает из контекста.

- прозвучало «вернёмся / пока пропустим / предлагаю» → сразу в todo или в бэклог;
- режим 3 сверяется с зафиксированным списком; память о разговоре — только дополнение;
- правило попадает в `CLAUDE.md`, потому что действует всегда, а не только по триггеру.

## 10. Граница с ревизором целостности

| | Ревизор целостности | Ревизор распространения |
|---|---|---|
| Объект | одна страница | система + итерация |
| Вопрос | соответствует ли правилам | согласовано ли после изменения, всё ли доделано |
| Триггер | перед сдачей | автоматически (режим 1) и по «закончили» (2, 3) |
| Актуальность спеки | **его зона** | не дублирует |
| Токен, которого нет | **его зона** (битая ссылка) | не дублирует |
| Токен есть, но перебит локально | не его зона | **его зона** |

Если в одном ходе срабатывают оба: сначала целостность (страница должна быть корректна), потом распространение (система вокруг неё).

## 11. Ложные срабатывания

- **осознанные отклонения** — компонент специально ведёт себя иначе; помечается в спеке, скилл такие пропускает;
- **наследие «не трогать»** — отдельный список в `ds-ripple.js`;
- **уже записанное** — проверка бэклога перед записью (см. дедупликацию);
- **совпадение по имени, не по смыслу** — класс `.sk-` в чужом файле может быть аббревиатурой; перед записью пункта — точечная проверка адреса.

## 12. Риски

| Риск | Что делаем |
|---|---|
| Бэклог превращается в свалку | правила раздела 7; ревизия бэклога — отдельной задачей, не этим скиллом |
| Пользователь пропустил единственную строку в чате | цифра открытых пунктов при каждом триггере |
| Ложное чувство покрытия | запрет на «всё чисто», раздел 8 в самом скилле |
| Триггер сработал не там | распознавание по форме сообщения + переспрос |
| Режим 3 рапортует по неполным данным | правило фиксации обещаний (раздел 9) |
| Скилл начнёт читать страницы «для верности» | прямой запрет: источник — вывод скрипта, чтение только по адресам |

## 13. Что войдёт в реализацию

1. `scripts/ds-ripple.js` — три скана + дедупликация против существующего бэклога.
2. `skills/ds-ripple-check.md` — режимы, триггер, шаблоны чата и бэклога, ложные срабатывания, расширение.
3. Правки `CLAUDE.md`: триггер «закончили», правило фиксации обещаний, места в чек-листах.
4. Обкатка на реальном случае Skeleton — проверить, что находит те самые компоненты с самодельными заглушками и не тонет в ложных.

Оценка: скрипт ~180–220 строк, скилл ~110 строк.
