Инициатива по ДС

Аудит: дизайн-система из коробки

Тип: Аудит / RFCОбновлено: 26.07.2026Покрытие: все компоненты ДС

Рабочая память инициативы: возвращаясь к вопросу, начинай с этой страницы. Цель — чтобы потребитель, подключив ДС, получал рабочий компонент (позиционирование, открытие, клавнавигация), а не мёртвую вёрстку. Сейчас переиспользуемое поведение и композиционные стили многих компонентов живут только на странице-витрине (в *.page.js внутри playground-обёрток и в inline-<style>), а не в глобальном рантайме/CSS.

Дорожная карта инициативы

Три фазы строго по порядку. Каждой фазе на этой странице соответствует свой раздел ниже.

Фаза 1 текущая

Правки существующих компонентов

Визуальная выверка: каждый компонент на странице ДС сравнивается с макетом в Pixso, расхождения — выравнивание, отступы, размеры, радиусы, цвета, отсутствующие состояния — правятся сразу, по компоненту за раз. Лог правок на этой странице не ведётся: фаза считается закрытой, когда пройдены все компоненты.

Дефекты другого рода — когда документация обещает класс, которого нет в CSS — живут в разделе «Парность документации и кода» ниже: они находятся скриптом и не требуют решений по визуалу.

трек не фаза

Парность документации и кода

Другой класс дефектов, чем в Фазе 1. Там — «нарисовано не так, как в макете», видно глазами. Здесь — «документация обещает класс, которого нет в CSS»: сборщик экрана копирует сниппет буквально и получает дефект, которого в макете нет. Находится скриптом, решений по визуалу не требует. Место в порядке работ — после текущих UI-правок компонентов, до экстракции рантайма Фазы 3.

Сверка 10 экранов с ДС · 26.07.2026

Откуда взяты позиции выше. Скриптом сопоставлены все class-токены экранов pages/screens/* (10 файлов) с 1051 классом из 48 файлов styles/*.css и с локальным <style> каждого экрана. Отдельно посчитаны инлайн-<svg>, .btn без размерного класса, hex-цвета и радиусы числом в локальном CSS.

Что показала сверка

  • Правило, зашитое в копируемый сниппет, соблюдается без исключений. Инлайн-<svg> на экранах — 0 при 267 вхождениях <i data-icon>. .btn без размерного класса — 0 из 83. Ни одного отступления на 10 экранах.
  • Все найденные нарушения — там, где документация обещает класс, которого нет в CSS. Сборщик исполняет сниппет буквально, поэтому расхождение doc↔code превращается в дефект экрана: 7 позиций в таблице выше, 6 из них — классы на состояние по умолчанию (chip--readonly, tab--horiz, ds-label--left, inp--m, st--neutral, crumbs__ellipsis), седьмая — живой визуальный дефект тона Алерта.
  • Переизобретение вместо переиспользования — 3 случая, разного происхождения. .cf-tip* на 07-CashFlow — свой тултип при живом .tip (причина — Фаза 3: рантайм позиционирования заперт в tooltip.page.js). .bulkbar* на 08-Payments — компонента нет в ДС, в Фазу 2. knr-*, t-zav / t-metrics / fin-grid, cbx — таблицы и чекбоксы руками, ждут Table / DataGrid.
  • Локальный CSS экранов в целом здоров. Из 0–34 локальных классов на экран почти все — раскладка (grid12, deal-grid, *-pos), это разрешено. Hex-цветов 2, радиусов числом 2 — на весь набор экранов.

Что это значит для инициативы

  • Документация уже работает — и потому расхождение с кодом стоит дефекта. Наращивать прозу вредно: каждая новая формулировка — ещё одна поверхность, на которой документация может разойтись с CSS. Правильное направление обратное: сокращать текст и переносить обязательность в код.
  • Источник API — только CSS. Канал доставки — только сниппет в specs/_cheatsheet.md. Третий реестр (json-манифест «возможности для сборщика») не нужен и вреден: ручная синхронизация реестров в этом проекте уже проваливалась — 33 строки specs/_index.md из 48 были устаревшими.
  • За md остаётся то, что кодом не выразить: когда компонент не использовать, границы с соседями, чего в ДС нет.
  • Фаза 3 нужна не всем компонентам, а тем, чей рантайм заперт на витрине. Признак теперь доказан фактом: такой компонент сборщик обходит и рисует свой (Tooltip → cf-tip). Это уточняет приоритет P1: первыми выносить те, у которых уже есть локальная замена на экранах.

Фаза 2

Недостающие компоненты

Пробелы текущей ДС относительно типового энтерпрайз-набора. Приоритет — по тому, что блокирует уже существующее и как часто встречается на экранах. Помеченное «уточнить» — сначала подтвердить необходимость с продуктом.

Фаза 3

В чём проблема

Проверил все scripts/*.page.js и inline-стили страниц. Поведение витрины написано заново на каждой странице внутри DOMContentLoaded + playground-IIFE и никуда не экспортируется. Композиционные стили (как .rm-block у RiskMetric) лежат прямо в <style> страницы.

Симптомы

  • Экран-эталон 02-Deal-v2 подключает только icons-data.js + ds-icons.js + screens-chrome.js. Рантайма компонентов нет — все состояния (открытый поповер, свёрнутый фильтр) нарисованы руками.
  • Реальное поведение заперто в витрине. placePop() + авто-flip + single-open (Popover), createSplitPane() drag/min-max (Splitter), bindRailTooltips() (NavPanel) — рабочий код, но внутри *.page.js, недоступен потребителю.
  • Композиционный CSS копипастится. .rm-block / .rm-field RiskMetric нет в styles/ — они инлайн на странице и уже скопированы в экран 02. Любая правка расходится в двух местах.
  • Сборщик экрана не знает возможностей. В чит-шите нет раздела «умеет из коробки»: какой скрипт подключить и какие data-атрибуты включают поведение.

Образец, к которому идём

  • ds-icons.js — самоинициализация: <i data-icon="…"> → SVG в currentColor, вызов dsIcons.apply(). Подключил — работает.
  • ds-illustrations.js — тот же принцип для <span class="illu" data-illu>.
  • input-kit.js (window.DSInputKit) — общий рантайм-фабрика для всех Input*. Логика поля вынесена из витрины, страница лишь вызывает makeInput().
  • ds-datepicker.js (window.DSDatePicker) — рантайм календаря: makeCalendar / openPicker + автоподключение кнопки-календаря полей InputDate / InputDateRange. Образец Фазы 2 → сразу из коробки.

Итог для каждого компонента: поведение → общий scripts/ds-<comp>.js (инициализация по классам/data-атрибутам, без привязки к DOM витрины); композиция-стили → глобальный styles/<comp>.css.

Матрица «из коробки»

Каждый компонент ДС: нужен ли рантайм-поведение, где оно живёт сейчас, где живёт композиционный CSS, доступно ли это потребителю без до-сборки, и что вынести.

page.js поведение заперто в витрине inline CSS инлайн на странице нет рантайма нет вовсе общий ✓ уже вынесен ✗ не из коробки ◐ частично ✓ из коробки

План экстракции

По компоненту за раз, проверка каждого — на живом экране (мокапе), а не на витрине.

  1. Аудит. Выписать, у каких компонентов поведение / композиция-стили живут только на витрине (эта таблица).
  2. Экстракция поведения. Переиспользуемую логику из *.page.js — в scripts/ds-<comp>.js: самоинициализация по классам/data-атрибутам, публичный API там, где нужен императивный вызов (Toast, SnackBar, Modal). Страница-витрина после этого лишь подключает общий скрипт + свой playground-код поверх.
  3. Экстракция стилей. Композиционные классы (как .rm-block) — в глобальный styles/<comp>.css, добавить @import в ds.css и styles.css. Убрать инлайн-дубли со страниц и экранов.
  4. Документация. В specs/_cheatsheet.md каждому компоненту — блок «умеет из коробки»: какой скрипт, какие data-атрибуты, какое поведение включается.
  5. Гейт парности. Прогнать проверку «документация = код» (панель ниже). Без неё экстракция создаёт новый слой обещаний, которые снова разойдутся с CSS.
  6. Проверка. Собрать/пересобрать реальный экран на общем рантайме — убедиться, что поведение работает без кода на странице.

Единый контракт рантайма

// scripts/ds-popover.js — образец: самоинициализация + императивный API
(function () {
  // авто: любой [data-popover] на странице получает поведение
  function bind(trigger) { /* open/close, placePop, flip, Esc, клик-вне */ }
  document.querySelectorAll('[data-popover]').forEach(bind);
  // императивно, где нужно строить динамически:
  window.DSPopover = { bind, place, closeAll };
})();

Гейт парности документации и кода

Скрипт-проверка, а не правило в тексте: md носит совещательный характер, гейт — обязательный. Гонять после каждой волны правок и перед приёмкой экрана, рядом с check_design_system.

  • Каждый класс из сниппетов specs/_cheatsheet.md и спек specs/*.md существует в styles/*.css. Сравнение — точным совпадением имени, не подстрокой (.inp--m ложно находится в .inp--multiline).
  • Каждый class-токен в pages/** определён либо в ДС, либо в локальном <style> этой же страницы.
  • Разметка Алерта несёт data-alert-tone; тон кнопок и ссылок внутри Алерта и Снекбара совпадает с тоном плашки.
  • .btn несёт размерный класс; icon-only кнопки несут aria-label.
  • В локальном CSS страниц и экранов нет hex-цветов и радиусов числом.
  • Локальный класс экрана, похожий на компонент (не раскладку), — сигнал: либо компонент не из коробки, либо его нет в ДС. Оба случая идут в лог правок или в Фазу 2, а не остаются на экране молча.

Порядок работ

Приоритет по частоте на экранах и по «разблокировке» зависимых компонентов. Экстракции предшествует парность: она дешёвая, механическая и снимает 7 из 8 позиций трека «Парность документации и кода».

P0
Парность документации и кода. После текущих UI-правок уже созданных компонентов и до экстракции рантайма.

P1

P3
