## 🔵 Что даст наибольший эффект (идеи оптимизации)

1. **Слой `styles/ds-docs.css`** (+ `ds-docs-playground.css`) — вынести повторяющийся хром страниц документации: `masthead`, `page`, `section/subsec`, `panel`, `panel.pg` + `pg__*`, `ctl`, `pg-select`, `toggle`, `ref-table`, `dev-table`, `code-panel`, `guide-card`, `anat`, `color-ref`, `page-foot`, `eyebrow`, `bullets`. Ожидание: **−250…300 KB** в `pages/`, единая точка правки внешнего вида документации.
2. **Один линк вместо десяти**: страницы документации подключают `ds.css` (как экраны) + `ds-docs.css` + свой per-page `<style>` только для уникального. Убирает класс ошибок «забыли зависимость».
3. **Генерация реестров скриптом**: `specs/_index.md` (версии/даты/зависимости), счётчики в `index.html`, полнота `ds-nav.js` — вычислять из masthead страниц, а не поддерживать руками. Сейчас 33 из 48 строк индекса устарели — ручная синхронизация не работает.
4. **Нормализовать контракт переменных компонентов**: либо определить `--btn-h/--ibtn-size/…` в размерных классах, либо убрать из базовых правил и оставить прямые значения. Сейчас fallback-значения в `var()` — скрытая теневая точка истины.
5. **Иконки**: разбить `icons-data.js` по группам или генерировать подмножество под фактический список глифов; страницы без иконок не грузят ничего.
6. **Общий playground-хелпер**: перенести в `pg-kit.js` повторяющиеся куски page-скриптов (построение контролов из декларации, redline-таблица через `getComputedStyle`, копирование в буфер). Ожидание: −150…250 KB в `scripts/`.

**Ошибка в моей проверке 4C.** Я проверил, что `pg-kit.css` выигрывает по
каскаду, но не проверил, что он вообще подключён на всех страницах
с конструктором. Правильная проверка — не «кто победит», а «есть ли второй
источник» — и только потом «кто победит».

**Починка.** Не возвращать удалённые объявления, а привести страницу к общей
конвенции: добавлены `styles/pg-kit.css` и `scripts/pg-kit.js` (как на соседней
`Radius.html`). Сплиттер `pg-kit.js` вставляет сам, поэтому третья колонка
сетки заполняется без правок разметки.

**Проверка после починки:** дети панели — `pg__controls, spl, pg__stage`;
сетка `360px 11px 444.83px`; паддинг контролов `26px 28px 30px`;
подпись отступает от края панели на 26px (была 0); сцена справа от контролов,
не под ними.

**Вторая находка того же класса: селект без обёртки `.pg-select`.**
На `Elevation.html` селекты остались выпадающими списками — и я сначала списал
это на правило «сегмент-контрол только для 2–4 опций». Настоящая причина другая:
`pg-kit.js` ищет селект как `ctl.querySelector('.pg-select') → select`,
а оба селекта лежали в `.ctl` напрямую. Без обёртки слой улучшения
не видит контрол вообще — ни сегмент-контрола, ни общих стилей селекта
из `ds-docs.css` (высота 40px, радиус, стрелка через `::after`) страница
не получала, рисовалась локальными правилами. Обёртка добавлена,
локальные `.ctl select` удалены.

**Сплошная сверка по всем `pages/*` и `scripts/*`:** ещё один такой же случай —
`Radius.html` (`#pgToken` без обёртки + свои `.ctl select`), исправлен так же.
Все остальные селекты — и литеральные в разметке, и собираемые в JS —
обёрнуты корректно.

**Сплошная сверка:** страниц с разметкой `pg__controls` без `pg-kit.css`
или `pg-kit.js` — **0**.

**Урок обеих находок один.** Правка «правило дублирует общий слой, удаляем»
верна только если общий слой на этой странице реально работает. Проверять
надо не «кто победит в каскаде», а сначала «подключён ли второй источник»
и «попадает ли элемент под его селектор».

## Волна 5 — радиусы вне шкалы (25.07.2026)

При починке селекта на `Radius.html` выяснилось, что общий хром сам рисовал
контролы радиусом 9px, которого в шкале нет — на странице, документирующей шкалу.
Строка сводки волны 4C «значений вне шкалы → 0» была верна только для `code.tok`
в общем слое; в инлайн-CSS страниц значения остались.

**Семантические алиасы, выбранные как канон для хрома документации** (по комментариям `radius.css`,
а не «по ближайшему px»):

| Было | Стало | Основание |
|---|---|---|
| `.pg-select select`, `.pg-text input` — 9px | `var(--radius-control)` = 8px | высота 40px = базовый контрол; алиас прямо называет «инпут». Не `--radius-field` (4px) — тот для компактных полей |
| `.code-panel__copy`, `.copy-btn` — 7px | `var(--radius-control-s)` = 6px | паддинг 5–6px, `--type-button-xs` — это кнопка XS |
| `.use-block`, `.anat__stage` — 14px | `var(--radius-xl)` = 12px | совпадает с соседними `.use-tile` / `.demo-card` / `.prop` |
| `.ds-nav__logo`, `.ds-nav__link` — 9px | `var(--radius-control)` = 8px | плитка 34px и строка меню — контролы |
| `.ds-nav__toggle` — 11px | `var(--radius-xl)` = 12px | плавающая кнопка 44px |
| инлайн-свотчи 22px в таблицах «Цвета» — 5px | `var(--radius-xs)` = 4px | 5px в шкале нет; на свотче 22px разница не видна |

Зона действия — только хром документации: `styles/*.css` и инлайн-CSS `pages/*`.
Стартеры в `scripts/` (например `image-slot.js`) из свипов исключены — они
работают и вне страниц ДС, где токенов нет.

**Сделано.** Три общих слоя (`ds-docs.css`, `input-pages.css`, `ds-nav.css`) — радиусов
числом больше нет. 5px → `var(--radius-xs)`: **424 вхождения в 41 странице**.

Свип шёл только по `pages/*`. `scripts/*` в него не входят и входить не должны:
в `scripts/image-slot.js` блиндовая замена один раз уже залезла в shadow-DOM CSS внутри строки
и была откачена: это копия стартер-компонента, намеренно самодостаточная
(сырые хексы, `system-ui`, соседние радиусы литералами), и на странице без
`styles/radius.css` токен не резолвится и угол схлопнулся бы в 0.

**Остаток — требует решения, не механики.** Подсчёт по всем 48 страницам пяти
каталогов `pages/*` (atoms, foundations, molecules, organisms, patterns):
14px — 78, 9px — 31, 7px — 6, 11px — 3. Делятся на две группы, и лечатся они по-разному:
- **дубли общего хрома** (`.toggle` 9px, `.anat__stage` 14px локально на десятках страниц) —
  правильно **удалить**, а не токенизировать дубль: в `ds-docs.css` они уже есть и уже на токенах;
- **одиночные декорации конкретной страницы** (`.navcell` 14px, `.ex-menu` 11px, `.ex-mi` 7px,
  `.seg button` 7px) — каждая ступень выбирается по смыслу элемента.

## Предлагаемый процесс исправления

Три волны по возрастанию риска; между волнами — проверка. Мелкая модель работает только там, где правка механическая и проверяемая скриптом.

**Волна 1 — «безопасное» (можно отдать младшей модели).**
R2, R12, M1–M8, M11, M13, M14, W10, W11 (R1/R3/R4/R9 из списка исключены как ложные).</br> Всё это — точечные строковые правки и синхронизация метаданных.
Правила исполнителю: только `str_replace_edit` по указанному в задаче anchor-тексту; ни одного изменения в `styles/*.css`; не переписывать разделы; после каждого файла ничего не «улучшать».

**Волна 2 — токены и мёртвый код (делаю я или модель по жёсткой таблице «было → стало»).**
R6–R8 (несуществующие токены), R5, R10, R11, W5–W9. Требует решения по каждому токену (определить / удалить / оставить), это дизайн-решение, а не механика.

**Волна 3 — рефакторинг хрома документации (только я).**
W1, W2, W4, W3, W12. Здесь ломается визуал 48 страниц, нужна пиксельная сверка до/после: сначала пилот на 2 страницах (одна простая + одна с конструктором), скриншот-диф, затем скриптовый перенос остальных.

**Защита от порчи (для любой волны, в т.ч. младшей моделью):**
- ветка/копии: перед волной — `pages/` и `styles/` копируются в `_backup-<дата>/`;
- задача формулируется как таблица «файл · старая строка · новая строка», без свободы формулировок;
- запрет: не менять версии/даты кроме указанных, не трогать `uploads/`, не переписывать разделы, не создавать файлы вне списка;
- после волны — прогон проверочного скрипта аудита (реестры, битые ссылки, неопределённые токены, баланс тегов, **все числовые подписи секций и сводка в шапке витрины**) + `check_design_system` + скриншоты 3 контрольных страниц;
- приёмка волны 3 — по гейту `skills/mockup-fidelity-review.md`.
